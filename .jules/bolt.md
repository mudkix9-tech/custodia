## 2026-07-20 - [Scoring Engine In-Memory Optimization]
**Learning:** In highly split relational calculations (like scoring modules), querying the database multiple times for subsets of the same parent entity (e.g., `processingActivities` by `organizationId`) creates massive query overhead. Furthermore, unconstrained relational queries (e.g., `db.query.processingTransfers.findMany({})` without a `where` condition) drastically slow down calculation runtimes as database size grows and load everything into system memory. Lastly, querying full model objects just to get counts is extremely heavy; selecting only `.id` or specific columns provides an immense speedup.
**Action:** Always pre-fetch common record arrays once and perform filtering in-memory (`.filter(...)`) in dependent modules, strictly avoid unconstrained global `findMany` queries, and select minimal query projection scopes when only lengths are needed.
